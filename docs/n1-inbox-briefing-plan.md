## 1. 질문 1 — 대상 화면을 어떻게 특정하는가

### 지금 있는 것

`extractStructuredDocumentList()`는 class/id가 아니라 **표의 의미 구조**(`table`/`role=grid`, 머리글 라벨)로 목록을 읽는다. `fieldForHeader()`가 이미 `보고일자·제목·부서·수발신자·보고자·붙임·상태`를 알아보고, `listName()`은 **화면 제목에 "받은문서"가 있으면 그것을 목록 이름으로 삼는다**. 즉 받은문서 화면을 읽는 능력은 이미 있다.

### 없는 것 두 가지

1. **"이 목록이 받은문서인가"의 판정.** 지금은 이름만 가져올 뿐 판정하지 않는다.
2. **그 화면을 나중에 다시 여는 방법.** 브리핑은 사용자가 그 화면을 보고 있지 않을 때 실행된다.

### 설계

- **브리핑 대상 지정(1회).** 사용자가 받은문서 목록에서 `브리핑 대상으로 지정` 버튼을 누르면, `captureDocumentListLocation()`과 같은 방식으로 **URL·프레임 경로·프레임 이름·조회 폼 필드**를 `chrome.storage.local`의 `saide.inboxLocation`에 저장한다. 설정에 URL을 타이핑하게 하지 않는다 — 온나라 목록은 대개 POST 조회라 주소만으로는 재현되지 않는다.
- **재현.** 수집 시에는 `restoreDocumentListLocation()`을 그대로 쓴다. 이 함수는 이미 저장된 폼을 백그라운드 탭에 복원해 제출한다.
- **판정.** 지정할 때는 **화면에 문서 목록 표가 있는가**만 가린다. 이름이 `받은문서`인지는 요구하지 않는다 — 온나라는 화면 제목을 목록과 다른 프레임에 그리는 경우가 있고, 무엇보다 이 지정은 사용자가 그 화면을 보면서 직접 누르는 행위다. 읽어 낸 목록 이름은 화면에 되보여 사용자가 확인하게 한다(`대상: 받은문서`). `isReceivedDocumentList()`는 **자동 경로**에서만 쓴다 — 지금 보고 있는 화면을 복제 없이 바로 읽어도 되는지 가릴 때다.

> ★ 저장하는 값은 **사용자가 직접 방문해 지정한 화면**의 것만이다. 임의 URL을 자동으로 열지 않는다.

## 2. 질문 2 — 열람 상태를 '미열람'으로 유지할 수 있는가

### 결론

**유지할 수 있다. 단 조건이 있다 — 문서를 열지 않아야 한다.**

- 열람 처리는 **온나라 서버가** 상세 화면을 내려 줄 때 기록한다. 확장은 브라우저 안의 클라이언트이므로 그 기록을 취소할 방법이 없다. 되돌리려면 온나라 내부 API를 추정해 호출해야 하는데, 이는 이 프로젝트가 지켜 온 fail-closed 원칙과 정면으로 어긋난다. **하지 않는다.**
- 반대로 **목록 화면을 읽는 것만으로는 열람 상태가 바뀌지 않는다.** 목록은 이미 사용자가 매일 여는 화면이고, 브리핑이 쓰는 값(제목·보고일자·수발신자·부서·붙임·상태)은 전부 그 표 안에 있다. 이것이 리뷰 원안이 "**목록 메타데이터만으로**" 분류하라고 한 이유다.

### 그래서 설정은 이렇게 만든다

사용자가 원하는 "브리핑 처리한 문서를 열람으로 바꿀 것인가"는 **"브리핑이 문서를 열 것인가"와 같은 질문**이다. 하나의 설정으로 합친다.

| `briefingReadPolicy` | 동작 | 열람 상태 | 비용 |
|---|---|---|---|
| `keep-unread` **(기본)** | 목록 표만 읽는다 | **그대로 미열람** | 모델 0~1회, 수 초 |
| `mark-read` | 브리핑에 실린 문서를 백그라운드 작업 탭에서 한 번씩 연다. 요약은 하지 않는다 | 열람으로 바뀜 | 문서당 수 초 |
| ~~`brief-body`~~ | 열어서 본문 요약까지 만든다 | 열람으로 바뀜 | **구현하지 않았다 — §12 참조** |

- 기본값은 `keep-unread`다. **되돌릴 수 없는 쪽을 기본으로 두지 않는다.**
- `mark-read`로 바꿀 때는 옵션 화면에서 한 줄로 고지한다 — "온나라 서버에 열람 기록이 남으며, 확장은 이를 되돌릴 수 없습니다."

### 코드가 스스로 검증한다

목록의 `상태`(또는 `열람`) 칸 값을 `readState`(`unread`/`read`/`unknown`)로 정규화해 원장에 남긴다. 그러면 **브리핑 실행 전후로 열람 상태가 바뀐 건수를 코드가 세어** 결과 카드에 그대로 표시할 수 있다.

> `열람 상태 변경 없음 (미열람 12건 유지)` — 모델의 주장이 아니라 코드가 대조한 사실이다(원칙 2).

### 표본으로 확인해야 할 것 (P0-5)

- [ ] 받은문서 목록에 열람 여부를 나타내는 **열**이 있는가, 아이콘·굵은 글씨로만 표시되는가
- [ ] 목록에서 제목 위에 마우스를 올리거나 **미리보기**를 띄우는 동작이 열람 처리를 유발하는가
- [ ] 목록 화면에 **일괄 열람확인** 기능이 있는가 (있다면 `mark-read`를 문서 열기 대신 그것으로 구현 — 훨씬 싸다. 단 클릭은 사용자 승인 후에만)

## 3. 질문 3 — 주기 실행과 "처리했는가"의 내부 관리

### 문서 정체성

`lib/cache/doc-results.ts`의 `documentIdentity()`와 같은 태도로 만든다. 받은문서는 목록 이름이 고정이므로 **제목 + 보고일자 + 수발신자**를 키로 삼는다.

```ts
// lib/inbox/identity.ts
export function inboxDocKey(row: InboxRow): string  // 정규화 후 fnv1a 64bit
```

> ★ 온나라 문서 ID를 읽을 수 있게 되면(P0-5) 이 함수 **하나만** 바꾼다. `doc-results.ts`가 같은 이유로 같은 구조를 쓰고 있다.

### 원장 — Dexie v5

```ts
// lib/storage/db.ts
this.version(5).stores({
  inboxDocs: 'key, firstSeenAt, briefedAt, category',
  inboxRuns: '++id, at',
});
```

| 필드 | 뜻 |
|---|---|
| `key` | 문서 정체성(기본키). 같은 문서는 몇 번을 다시 읽어도 한 행이다 |
| `title` `reportDate` `sender` `department` `hasAttachment` | 목록에서 읽은 값 |
| `readState` | `unread`/`read`/`unknown` — 열람 상태 검증의 근거 |
| `firstSeenAt` | 처음 목록에서 본 시각 |
| `briefedAt` | **브리핑에 실린 시각. 비어 있으면 "아직 처리 안 함"이다** |
| `category` `reason` `dueDate` | 분류 결과와 그 근거, 코드가 제목에서 뽑은 기한 |
| `openedAt` `dismissedAt` `taskId` | 사용자가 열었는가 · 넘겼는가 · 일정으로 등록했는가 |

`inboxRuns`는 실행 한 번의 기록이다 — `at`·`trigger`(`alarm`/`interval`/`manual`/`startup`)·`scanned`·`added`·`briefed`·`readStateChanged`·`error`. 도구 탭의 작업 기록과 같은 역할이되, 브리핑은 하루에도 여러 번 돌므로 50건 상한의 작업 기록을 밀어내지 않도록 자리를 나눈다.

### 실행 한 번의 흐름

```
목록 읽기 → 행마다 key 계산
  ├ 원장에 없다         → 새 문서. 범위 필터 → 분류 → 원장에 추가(briefedAt 미정)
  ├ 있고 briefedAt 있음  → 건너뛴다 (readState 변화만 갱신)
  └ 있고 briefedAt 없음  → 지난번에 못 실은 문서. 이번 브리핑에 포함
→ 브리핑 카드 생성 → 실린 문서에 briefedAt 기록
```

- **보관 정리.** `briefingRetentionDays`(기본 60)보다 오래된 행은 지운다. 목록에서 사라진 문서도 함께 정리한다.
- **다시 브리핑.** 카드의 `다시 분류` 버튼은 `briefedAt`을 비우고 재실행한다(B1의 `다시 분석`과 같은 태도).

## 4. 질문 4 — 스케줄링과 브라우저 의존성

### 정확한 사실

**맞다. Edge가 실행 중이어야만 onNara.sAIde도 동작한다.** MV3 확장은 브라우저 프로세스 안에서만 살아 있다. Edge를 완전히 종료하면 서비스 워커도 `chrome.alarms`도 멈춘다. 이것은 설계 선택이 아니라 플랫폼의 성질이다.

다만 **사이드패널이 열려 있을 필요는 없다.** 이 구분이 중요하다.

| 무엇 | 필요한가 | 근거 |
|---|:--:|---|
| Edge 실행 중 | **필수** | 확장의 수명이 브라우저의 수명이다 |
| 사이드패널 열림 | 불필요 | `chrome.alarms`가 서비스 워커를 깨운다. 기한 알림이 이미 이렇게 동작한다 |
| 온나라 탭 열림 | 권장(기본 조건) | 세션 확인 비용을 줄이고, 로그인 만료 상태에서 헛도는 것을 막는다 |
| 온나라 로그인 세션 | **필수** | 세션이 끊기면 목록 대신 로그인 화면이 온다 |

### 완화 수단과 그 한계

1. **Edge 백그라운드 실행.** Edge 설정의 "Microsoft Edge가 닫혀 있을 때 백그라운드 앱 계속 실행"(정책명 `BackgroundModeEnabled`)을 켜면 창을 닫아도 확장이 살아 있다. → 기관 배포 키트(B7)의 정책 JSON 견본에 넣을 항목이다. **단 온나라 로그인 세션은 그와 무관하게 만료되므로 실효는 제한적이다.**
2. **OS 작업 스케줄러로 Edge를 자동 실행.** 가능하지만 온나라 로그인(인증서·GPKI)을 무인으로 통과할 수 없어 **실무에서 쓸 수 없다.** 권고하지 않는다.

> ★ 그러므로 이 기능의 현실적 설계 전제는 **"사용자가 온나라에 로그인한 채 브라우저를 쓰는 동안"**이다. 그 전제를 숨기지 않고, 실행하지 못한 이유를 공유/공람 탭에 그대로 적는다(`온나라 세션이 만료되어 09:12 실행을 건너뛰었습니다`).

### 트리거 세 가지

| 트리거 | 조건 | 설정 |
|---|---|---|
| 하루 1회 | `briefingHour`(기본 9시) 이후 첫 확인, 하루 한 번. **기본값** | `briefingEnabled` |
| 주기 확인 | 업무시간 창 안에서 `briefingIntervalMinutes`(30·60·120·240분)마다 | `briefingIntervalMinutes > 0` |
| 수동 즉시 | `@브리핑` 명령 또는 공유/공람 탭의 `지금 확인` | 언제나 가능 |

`saide.inboxBriefing` 알람의 주기는 `alarmPeriodMinutes()`가 설정에서 뽑고, 설정이 바뀌면 `onSettingsChanged`가 알람을 다시 만든다 — 확인 주기보다 성기게 깨우면 그 주기를 지킬 수 없다. 알람은 브라우저를 켠 뒤 최대 주기만큼 늦게 오므로 `chrome.runtime.onStartup`에서도 한 번 확인한다 — `alerts.ts`가 이미 쓰는 방식이다.

주기 확인에만 걸리는 제동이 셋 있다.

- **업무시간 창**(`briefingHour`~`briefingEndHour`, 기본 9~18시)과 **주말 제외**(`briefingSkipWeekend`, 기본 켜짐). 하루 1회 모드에는 적용하지 않는다 — 저녁에 브라우저를 처음 켠 사용자가 그날의 브리핑을 통째로 잃어서는 안 된다.
- **연속 실패 백오프**(`backoffFactor`). 3회 연속 실패하면 간격 2배, 6회면 4배. 실패의 거의 전부는 세션 만료이고, 그것은 다음 30분 안에 저절로 낫지 않는다.
- 간격의 기준은 마지막 **성공**이 아니라 마지막 **시도**다. 성공만 보면 세션이 끊긴 동안 매 알람마다 같은 실패를 되풀이한다.

주기를 짧게 잡아도 알림이 쏟아지지 않는다. `planBriefing`이 `briefedAt`이 찍힌 문서를 다시 싣지 않고, 실을 것이 없으면 `briefingNotice()`가 `null`을 돌려 알림 자체가 뜨지 않는다.

### 서비스 워커 수명과 실행 주체

| 상황 | 누가 수집하는가 | 누가 분류하는가 |
|---|---|---|
| 패널이 열려 있다 | 패널이 SW에 요청(기존 경로 그대로) | 패널 (규칙 + 모델 1회) |
| 패널이 닫혀 있다 | **서비스 워커가 직접** | **규칙만**. 모델은 부르지 않는다 |

> ★ LLM 호출은 서비스 워커에서 하지 않는다 — 이 프로젝트의 최초 설계 결정이다(`background.ts` 머리말). 패널이 닫혀 있을 때는 **규칙 분류만으로 알림을 띄우고**, 모델 분류는 사용자가 알림을 눌러 패널을 연 순간에 1회 수행한다. 오프스크린 문서에 LLM을 올리는 방법도 있으나(PDF 추출이 이미 오프스크린을 쓴다), **1단계에서는 하지 않는다.** 규칙만으로도 브리핑은 성립하고, 아키텍처를 건드리는 비용이 그 이득보다 크다.

### 놓치면 사고가 나는 지점

**작업 탭 잠금이 지금 패널 쪽에만 있다.** `workTabLock()`은 `lib/automation/jobs.ts`(zustand 스토어 = 패널 문서)에 있다. 서비스 워커가 알람으로 수집을 시작하면, 패널이 동시에 돌리는 첨부 받기·문서 읽기와 **작업 탭이 겹친다.**
→ **서비스 워커 측 잠금을 새로 만든다**(`lib/browser/sw-lock.ts`). 패널이 여는 `READ_DOCUMENT`·`DOWNLOAD_ATTACHMENTS`와 브리핑 수집이 같은 잠금을 거친다. 이것은 선택이 아니라 필수 항목이다.

## 5. 질문 5 — 대상 문서의 범위

### 1단계 — 전체 / 키워드 (모델 0회)

```ts
briefingScope: 'all' | 'keywords'
briefingKeywords: string[]         // 포함(OR). 비어 있으면 전체와 같다
briefingExcludeKeywords: string[]  // 제외. 포함보다 우선한다
briefingFields: ('title' | 'sender' | 'department')[]  // 기본 셋 다
```

대조는 `document-list.ts`의 `searchable()`과 같은 정규화(NFC · 공백·구두점 제거 · 소문자)를 쓴다. `예산 편성`과 `예산편성`이 갈리지 않아야 한다. 범위 밖 문서는 버리지 않고 `category: 'filtered'`로 원장에 남긴다 — **나중에 키워드를 넓혔을 때 지난 문서를 되살릴 수 있어야 하고, "몇 건을 걸렀는지"를 화면에 보여 주어야 사용자가 필터를 신뢰한다.**

### 분류 — 코드가 먼저, 모델은 보강

| 갈래 | 규칙(모델 0회) |
|---|---|
| `deadline` 기한 임박 | 제목에서 날짜·기한 표현을 뽑는다. **`lib/schedule/nl-date.ts`·`due-date.ts`를 그대로 재사용**한다 |
| `mine` 내 업무로 보임 | 설정 키워드 일치, 또는 과거에 `/조치`로 일정을 등록한 문서들의 토큰과 겹침(`lib/memory/keyword.ts`의 BM25) |
| `notice` 단순 공람 | 나머지 |

모델 분류(패널이 열려 있을 때 1회)는 `lib/schedule/classify.ts`를 본떠 만든다 — `temperature: 0`, `format` JSON 스키마, `num_ctx` 4096 제한, 문맥 미첨부. **제목 N개를 한 번에 보내고 갈래만 받는다.** 기한 날짜 값 자체는 언제나 코드가 뽑은 것을 쓴다(원칙 2 — 모델에게 사실을 맡기지 않는다).

### 2단계 — 관심도 학습 (RAG)

사용자가 브리핑 카드에서 누른 `관심`/`관심 없음`이 곧 학습 표본이 된다. B4 피드백 저장소를 그대로 쓰되 `kind: 'inbox-relevance'`를 추가한다.

```
관심 표시한 제목 → bge-m3 임베딩 → memory store의 별도 컬렉션(interest)
신규 제목 → 임베딩 코사인 + BM25 → RRF 결합 → 임계값 이상이면 'mine'
```

- **선행 조건은 B9(하이브리드 검색)다.** 공문 제목은 `2026-1234호`·`제3차 기본계획` 같은 정확 일치 질의가 많아 벡터 단독으로는 놓친다. 진단서가 B9을 S05·S06의 선행 작업으로 둔 이유와 같다.
- 임계값과 근거 문서를 카드에 함께 보여 준다 — "`○○사업 정산` 문서를 관심 표시했기 때문" 정도의 한 줄. 이유를 모르는 자동 분류는 신뢰를 얻지 못한다.

## 6. UI

### 어디에 두는가 — 공유/공람 탭을 신설한다 (결정 완료 · §11)

당시 패널은 `AI · 일정 · 도구` 세 탭이었고, 일정·도구 탭은 이미 개수 배지를 달고 있었다(`view-tab-count`). **탭 `공유/공람`**을 신설하고 **아직 처리하지 않은 문서 건수 배지**를 단다.

> **구현 결과(2026-09-21):** 탭 차례는 `AI · 공유/공람 · 일정 · 도구`다. 명령을 내리는 자리(AI)를 맨 앞에 두고, 공유/공람을 그 다음에 둔다.

> ★ 이 기능의 목적은 "매일 열 이유를 만드는 것"이다(진단 ②). 도구 탭 안의 한 섹션으로 넣으면 그 목적을 잃는다. 탭이 넷으로 늘어나는 비용을 치를 값이 있다.
> 대안(도구 탭 내 섹션)을 택한다면 탭 배지만이라도 별도로 띄워야 한다.

### 화면 구성

```
[공유/공람 브리핑]                                      [지금 확인]
09:04 확인 · 목록 12건 · 새 문서 7건
─────────────────────────────────────────────
기한 임박 2건
  □ ○○사업 정산자료 제출        교육지원과 | 09-19 | 첨부2  D-2
     [문서 열기] [일정 등록] [관심] [넘기기]
내 업무로 보임 3건   …
단순 공람 2건 (접힘)
범위 밖 4건 (접힘)
```

- 머리말은 **바뀐 것만** 말한다. 열람 상태가 바뀐 문서가 있을 때만 그 건수를 올리고, 그대로인 날에는 아무 말도 하지 않는다(2026-09-21 변경 — "변경 없음"은 정상이고, 정상은 머리말을 차지할 이유가 없다). 대상 화면 이름도 지정 전에만 보인다.
- `문서 열기`는 **사용자가 누를 때만** 동작하고, 누르는 순간 열람 처리됨을 버튼 툴팁에 적는다.
- `일정 등록`은 기존 `TaskRegisterCard` 흐름을 재사용한다 — 이것이 진단 ②가 말한 "일정 탭으로의 자동 유입 경로"다.

> **구현 결과(2026-09-21):** `일정 등록`은 카드 안에서 **세 걸음**으로 펼쳐진다(`InboxTaskDraft`).
>
> 1. **알린다.** 누르는 즉시 등록하지 않는다. "본문을 여는 순간 온나라에 열람 기록이 남아 이 문서는 미열람 → 열람으로 바뀌며 되돌릴 수 없다"를 먼저 보이고, 그 자리에 `목록 값으로만 등록 (미열람 유지)`을 나란히 둔다. 열람을 감수하지 않는 길이 반드시 남아 있어야 한다.
> 2. **읽는다.** 사용자가 누르면 `READ_DOCUMENT`로 본문을 읽고, 핵심·조치사항과 **같은 스키마·같은 원문 대조**로 일정 후보를 뽑는다(`lib/inbox/task-draft.ts`). 본문이 실제로 열린 뒤에는 원장에도 사실대로 적는다 — `readState: 'read'`와 `taskReadAt`(열람의 세 번째 사유. `openedAt`·`markedReadAt`과 섞지 않는다).
> 3. **확인받는다.** 뽑은 값은 폼(제목·기한·시각·메모)에 채워질 뿐이고, 저장은 사용자가 누를 때 일어난다. 근거 문장·원문 확인 배지·다른 후보를 함께 보인다. 모델을 부르지 못하면 목록 값으로 폼을 채우고 그 이유를 적는다 — 이미 문서를 연 뒤에 등록조차 못 하면 사용자는 열람 기록만 내주게 된다.
- 알림을 누르면 공유/공람 탭이 열린다. `lib/panel/links.ts`에 `{ tab: 'inbox' }` / `{ tab: 'inbox', docKey }`를 추가하고 `PANEL_LINK_URI_PATTERN`을 함께 넓힌다(그 파일의 경고대로 **문법과 허용 목록은 한곳에서** 고친다).

## 7. 원칙과의 충돌, 그리고 해소

진단서 §7의 첫 원칙은 **"자동 저장·자동 실행 경로를 만들지 않는다. 브라우저 조작은 사용자가 누를 때만 일어난다"**이다. 스케줄 브리핑은 이 원칙과 정면으로 만난다. 다음 네 가지로 해소한다.

1. **기본값은 꺼짐.** `briefingEnabled`는 기본 `false`다. 켜는 순간이 사용자의 명시적 승인이며, 그때 무엇을 자동으로 하는지(백그라운드 탭을 만들어 목록을 읽는다) 화면에 적는다.
2. **읽기만 한다.** 자동으로 하는 일은 **목록 조회 하나**다. 등록·수정·삭제·제출은 없다. 상태를 바꾸는 유일한 동작(문서 열기)은 기본값에서 아예 일어나지 않는다.
3. **사용자 화면을 건드리지 않는다.** 기존 `readDocumentInBackground`와 같이 **작업 탭을 복제해** 거기서 열고 닫는다. 보고 있던 탭은 그대로다.
4. **전부 기록에 남는다.** `inboxRuns`에 언제·무엇을 근거로 실행했는지 남고, 공유/공람 탭에서 볼 수 있다.

→ 원칙 문구를 이렇게 다듬을 것을 권고한다: *"상태를 바꾸는 조작은 예외 없이 사용자가 누를 때만 한다. 읽기는 사용자가 명시적으로 켠 범위 안에서만 자동으로 일어날 수 있다."*

| 작업 탭 충돌 | 첨부 받기·문서 읽기 실패 | `lib/browser/sw-lock.ts` — **필수 항목** |
| 목록에 수백 건 | 분류 비용·화면 과부하 | 수집 상한 200건(추출기 자체는 500행 상한), 브리핑 노출은 갈래별 상위 N건 + 접기 |
| 제목이 원장에 쌓인다 | 개인정보 심사 지점 | 피드백 저장소가 제목을 피한 것과 달리 **여기서는 불가피하다.** 보관 기간 설정 + 전체 삭제 버튼 + 옵션 화면에 저장 내역 고지. 전부 로컬 IndexedDB |
| 자동 실행이 원칙과 충돌 | 제품 정체성 훼손 | §7의 네 가지 |

## 12. 구현하며 바뀐 것

계획과 다르게 간 것만 적는다. 이유가 있는 이탈이고, 문서를 사실에 맞춘다.

| 항목 | 계획 | 실제 | 왜 |
|---|---|---|---|
| 열람 정책 | `keep-unread` / `mark-read` / `brief-body` 3갈래 | **2갈래**(`keep-unread`·`mark-read`) | `brief-body`(본문 요약)는 모델 파이프라인이 더 필요하다. 동작하지 않는 선택지를 설정 화면에 두지 않는다. 저장된 값이 `brief-body`면 기본값으로 떨어지며, 기본값은 상태를 바꾸지 않는 쪽이다 |
| `mark-read` 실행 조건 | 브리핑한 문서를 연다 | **받은문서 목록을 보고 있는 탭에서 확인할 때만** | 문서를 여는 유일한 길이 "그 목록에서 제목을 누르는 것"이다. 목록이 화면에 없으면 열 대상을 찾을 수 없어, 조용히 실패하는 대신 아무것도 하지 않는다 |
| 열람 처리 기록 | `openedAt` 하나 | `openedAt`(사용자) / `markedReadAt`(설정) 분리 | 섞으면 아직 읽지 않은 문서가 처리된 것처럼 목록에서 사라진다 |
| 설정 이름 | `briefingBodyLimit` | `briefingOpenLimit` | 본문을 읽지 않으므로 "여는 문서 수"가 맞는 이름이다 |
| 공유/공람 판정 | 목록 이름에 `받은문서`가 있으면 참 | 추출 단계에서 `received` 근거를 남기고 그것만 본다 | `listName()`은 이름을 **찾지 못했을 때도** 기본 표시로 `받은문서`를 돌려준다. 이름만 보면 아무 목록이나 브리핑 대상으로 등록된다(시험으로 걸렸다) |
| 제목 기한 표기 | `due-date.ts` 그대로 재사용 | `expandDeadlineNotation()`을 앞에 둔다 | 본문 파서는 `9. 22.`처럼 연도도 월·일 글자도 없는 표기를 일부러 거른다(본문의 항목 번호 때문). 제목에는 `(9. 22.까지)`가 흔해, **기한 낱말이 바로 뒤에 붙은 경우에만** 명시 표기로 고쳐 넘긴다. 본문 파서는 그대로 둔다 |
| 화면이 보여 주는 것 | 이번에 새로 들어온 문서 | **아직 처리하지 않은 문서** | 새 문서만 보이면 아침 알림을 놓친 날 화면이 비어 있다. "새로 들어온 n건"은 머리말의 수치로 남긴다 |
| 지정 요청의 전달 | `LOCATE_INBOX`를 탭에 보낸다 | **목록이 있는 프레임을 먼저 찾아** 그 프레임에 보낸다 | 추출이 아닌 메시지는 최상위 프레임에만 전달된다(`dispatchContent`). 온나라 목록은 하위 iframe에 있어, 최상위에 대고 물으면 표가 없어 `현재 화면에서 받은문서 목록을 찾지 못했습니다`가 난다 — 실제로 났고 고쳤다. 문서 한 건을 여는 경로가 이미 같은 이유로 `sourceFrameId`에 대고 묻는다 |
| 받은문서 판정 | 지정·수집 양쪽에서 이름표를 요구 | 지정은 **표가 있는가**만, 수집은 **복원한 자리에 표가 떴는가**만 | 화면 제목이 다른 프레임에 있으면 목록 프레임에서는 그 이름을 읽을 수 없다. 지정은 사용자의 명시적 행위이고, 수집은 그 사용자가 지정한 자리를 그대로 복원하는 것이다. 다만 **복제 없이 지금 화면을 바로 읽는 빠른 경로**에서는 이름이 같은지(또는 화면이 스스로 받은문서라고 밝혔는지) 따진다 — 사용자가 열어 둔 다른 목록을 잘못 브리핑하지 않기 위해서다 |
| 빈 목록 | 행이 없으면 목록이 아니다(추출기 기본 동작) | **행이 없어도 목록으로 읽는다** | 받은문서가 0건인 날(`해당 문서가 없습니다`)에도 머리글은 그대로 있다. 표째 버리면 "목록이 없는 화면"과 "비어 있는 목록"을 구분할 수 없어, 문서가 없는 날 지정이 막힌다 — 실제로 막혔다. 대신 빈 표는 머리글 열이 3개 이상일 때만 인정하고, 수집할 때는 1.5초 더 지켜본 뒤 받는다(행이 뒤따라 그려지는 화면에서 0건으로 단정하지 않기 위해서다) |
| 작업 탭 잠금 | 계획대로 신설 | `lib/browser/sw-lock.ts` 신설 + **브리핑은 바쁠 때 물러난다** | 줄을 세우면 사용자의 `/요약`이 브리핑 뒤에서 기다린다 |
| 다중 페이지 수집 | 첫 페이지만 읽음 | **전체 페이지 순회 수집 (`inbox-pages.ts`)** | 받은문서가 여러 페이지에 걸쳐 수신되는 기관 환경을 위해 페이징 버튼을 추적하여 전체 페이지를 일괄 수집 |
| 일정 등록 연동 | 단순 즉시 등록 버튼 | **할 일 작성 초안 모달 (`InboxTaskDraft`) 지원** | 제목만으로 일정을 넣기보다 공문 맥락을 살려 세부 할 일과 기한을 다듬어 넣을 수 있도록 초안 작성 기능 추가 |

### 알려진 한계

- **관심도 학습(M5)은 미착수.** B9(하이브리드 검색) 위에 올려야 한다. 다만 표본은 지금부터 쌓인다 — 카드의 `맞음`/`틀림`이 `inbox-relevance`로 저장된다
- **열람 열이 없는 판본**에서는 `unknown`이 되어 열람 상태 변화를 셀 수 없다. 바뀐 건수를 알리지 못할 뿐 브리핑 자체는 그대로 동작한다
