# onNara.sAIde 참조 프로젝트 분석 및 서비스 제안

분석일: 2026-09-17. 대상은 이 작업 폴더의 두 참조 프로젝트 복사본이다. 현재 구현에 대한 관찰, 통합 시 예상 문제, 신규 서비스 제안을 구분한다. 새 제품 구현이나 운영 온나라 접수는 수행하지 않았다.

## 1. 종합 판단

권장 제품은 Edge 오른쪽 사이드패널에서 현재 온나라 문서의 맥락을 이해하고 읽기·검색·작성·업무처리를 돕는 로컬 AI 업무 도우미다.

- 제품 기반: sAIde의 WXT·React·TypeScript, Ollama 클라이언트, 대화 UI, 스트리밍, 저장·검색, 작업 취소, 승인 구성요소.
- 온나라 연결: 문서배부기의 프레임 탐색, 목록 구조화, 부서 명단 동기화, 팝업 연결, 문서·담당자·결과 검증.
- 신규 핵심: 문서 ID 중심 맥락 관리, 본문·첨부 읽기, 업무용 지식 저장소, 서비스별 구조화 결과와 근거 표시.
- 두 확장의 UI와 상태 저장 방식을 그대로 중첩하기보다, sAIde 기반 안에 온나라 전용 어댑터와 업무 서비스를 분리해 이식하는 편이 적합하다.

## 3. 온나라 AI 문서배부기 분석

위치: `onnara-ai-document-distributor/onnara-ai-document-distributor-main/`

### 구성과 실행 흐름

- `manifest.json`: MV3 1.2.0. 온나라 지정 호스트와 범정부 AI 호스트 권한. content script는 document_start에 최상위 문서와 해당 팝업에 주입된다.
- `content.js`: 페이지 종류 판별, 같은 출처 프레임 재귀 탐색, 접수 목록 읽기, 명단 로딩, 결과 표시, 체크 준비, 팝업 보호와 최종 결과 감시.
- `sidepanel.js`: 활성 온나라 탭에 상태·명령을 전달한다. content가 만든 HTML 뷰를 받고 약 1초마다 동기화한다. 브라우저 Side Panel이 기본이며 DOM Shadow 패널은 대체 경로다.
- `background.js`: 원격 RAG와 Chat 호출, 설정, 명단 revision, 대기 작업 상태, 일회용 승인, 감사기록 관리.
- `lib/core.js`: 문자열·명단 정규화, 지문, RAG 질의·청크 정리, 구조화 응답 파싱, 추천 검증, CSV 이스케이프.
- `samples/`: 업무분장·배부이력의 Markdown/JSON/CSV 자료 계약. 업무의 포함·제외 범위, 적용일, 정정 이력 등을 설계에 재사용할 수 있다.

주요 처리 순서:

1. 접수대기함과 현재 로그인 과를 확인한다.
2. 조직도 DOM에서 같은 과의 성명·부서·직위를 읽고 배부 가능 인원을 선택한다.
3. 선택 문서 또는 현재 페이지 목록의 메타데이터를 읽는다.
4. 업무분장·배부이력 RAG를 검색한다.
5. 생성 모델에 문서 메타데이터, 검색 근거, 임시 후보 ID를 보내 담당자를 추천받는다.
6. 후보·근거·명단 revision·신뢰도 조건을 검증한다.
7. 같은 담당자 문서끼리 체크 준비한다.
8. 기존 온나라 일괄접수 및 담당자 지정 팝업을 통해 실제 선택을 수행한다.
9. 최종 확인 의도와 실제 처리완료 결과를 별도로 기록한다.

### 중요한 온나라 화면 계약

| 구간 | 구현에서 사용하는 구조 |
|---|---|
| 접수대기함 | `main.do` 아래 `_MAIN` iframe, `/bms/dctlist/act_wil.do` |
| 문서 행 | `form[name="mainFrm"]`, `input[name="chkDocId"]`, 가장 가까운 tr |
| 제목 | `input[name="chkDocTitle"]` 우선 |
| 열 읽기 | thead 텍스트로 인덱스를 찾고, 없으면 fallback 위치 사용 |
| 현재 과 | `SELECTED_DUP_LOGIN_ID` 선택값에서 부서 ID·표시 과명 |
| 조직도 | `/bms/org/orgtreeset.do`, 같은 부서와 전체 건수 확인 |
| 일괄접수 | `/bms/dctenf/BmsDctEnfMultiAccept.do`, `td_result_*` 문서 집합 |
| 담당자 지정 | `/bms/dctenf/BmsDctEnfPathView.do`, `frmPath` → `rightIframe` |
| 최종 지정 결과 | `#pathList`의 업무담당 행 |

일괄접수의 처리경로 하나가 선택 문서 전체에 적용되므로 서로 다른 담당자의 문서를 한 번에 묶으면 안 된다. 사용자 ID나 inline handler 인수를 조립하지 않고, 화면의 표시 인물을 매칭해 기존 클릭·추가 로직을 사용한다.

### 보존할 검증 장치

- 자동접수·암호화 표시·비활성 문서 제외.
- 현재 과 명단의 부서 ID, 건수, 중복, 안정된 두 스냅샷 검사.
- 체크 해제한 담당자를 추천과 실제 지정 양쪽에서 제외.
- 모델의 임시 후보 ID를 로컬 명단에 매핑하고 실제 문서 ID는 모델에 보내지 않는 방식.
- 검색 근거가 없거나 근거 청크가 맞지 않으면 검토 필요로 처리.
- 명단 revision, 페이지 지문, 문서 ID 집합, 팝업 연결, 실제 지정자 재검증.
- 브라우저 프로필 안에서 native 접수 흐름 하나만 활성화하는 lease.
- 자동확인 2분 일회용 토큰, 사람 모드의 자동 승격 금지, 조건 변경 시 강등.
- 처리 의도 이후 결과가 불분명하면 재실행 전 수동 결과 대사.
- 실제 처리완료를 확인해야 성공으로 기록. 클릭 성공을 접수 성공으로 취급하지 않음.

### 범위와 로컬 전환의 차이

현재 AI 입력은 제목·발송부서·구분 및 선택적 문서번호·수신일자다. **본문·첨부파일 추출기는 없다.** 상세보기 본문의 selector도 참조 문서상 미확정이다.

RAG는 `api.clovastudio.go.kr/v1/rag42/search`, 생성은 해당 호스트의 Chat Completions를 호출한다. API 주소만 localhost로 치환해서 끝나지 않는다. 자료 적재·청크화·로컬 검색·모델 요청/응답 계약을 새로 연결해야 한다. 원격 호출의 28초 전체 제한도 로컬 모델의 로딩·생성 지연에 맞춰 재설계해야 한다.

모델이 출력하는 0~100 신뢰도는 보정된 정답 확률이 아니다. 로컬 모델로 바꾼 뒤 기존 60/85 임계값의 품질이 유지된다고 가정하지 않는다.

## 4. sAIde 분석

위치: `sAIde/`

### 구조와 재사용할 부분

- `wxt.config.ts`: React/WXT 빌드, MV3, 사이드패널·설정·단축키·권한. 현재 Chrome 빌드 기준.
- `src/entrypoints/sidepanel/App.tsx`: 현재 탭, 페이지·화면 첨부, 프리셋, 상태, 임베딩 큐.
- `src/lib/chat/store.ts`: 대화 상태·저장·생성·중단·재생성·승인 대기, 늦게 도착한 결과의 소유권 검사.
- `src/lib/ollama/`: `/api/chat` 스트리밍, `/api/embed`, 모델 목록·기능 확인, 오류·시간 제한·성능 기록.
- `src/entrypoints/background.ts`: 탭·메뉴 이벤트, 메시지 검증, 스크립트 주입·캡처·브라우저 행동 라우팅.
- `src/entrypoints/injected.ts`: Readability와 innerText 추출, 일반 DOM 찾기·입력·클릭. 기본 주입과 메시지 대상은 최상위 프레임이다.
- `src/lib/agent/`: 읽기·요소 찾기·스크롤·캡처·탭 목록·클릭·입력·이동의 8종 도구. 변경 행동은 승인하고 반복·시간 제한을 둔다.
- `src/lib/browser/`: 요청·캡처 대상 검사와 동일 문서·동일 요소·행동에 묶이는 120초 일회용 승인.
- `src/lib/storage/`: 설정·프리셋은 chrome.storage.local, 대화·메시지·기억은 Dexie/IndexedDB.
- `src/lib/memory/`: 유휴 임베딩, 청크 저장, 코사인 검색, 출처 번호를 붙이는 검색 답변.

LLM 요청은 패널 문서가 수행하고 서비스 워커는 브라우저 연결을 맡는다. 패널을 닫아도 작업이 영속적으로 계속되는 시스템은 아니다.

### 검색·컨텍스트의 현재 한계

- 기본 context 4,096, 페이지 읽기 예산 2,000 추정 토큰. 요청 직전 전체 입력이 context의 70%를 넘으면 거부.
- 긴 본문 자동 재분할·단계별 종합은 아직 별도 설계가 필요하다.
- 기억은 사용자가 패널로 읽힌 페이지에 한정되며 opt-in이다.
- 약 8초 유휴 후 임베딩. 한 페이지는 최대 4개, 각 약 400토큰 청크.
- 대기 큐는 패널 메모리 안에 있어 종료 시 사라진다.
- 같은 URL 기억은 덮어쓰며 검색 결과도 URL별 최적 청크 하나로 묶는다.
- `/기억`은 상위 최대 5개 페이지의 청크를 검색하고 각 400자 발췌를 모델에 넣는다.
- 검색은 전체 벡터 순회다. 대용량 공문 지식베이스의 검증된 검색 엔진으로 간주할 수 없다.
- 모델 이름·벡터 차원은 확인하지만 같은 태그의 모델 교체를 구분할 digest 관리가 더 필요하다.
- endpoint 설정은 HTTP/HTTPS 원격 주소도 허용하므로 로컬 전용은 현재 강제되지 않는다.
- 페이지 첨부와 스크린샷 자체는 대화 메시지와 같은 방식으로 영구 보존되지 않는다. 근거 재현을 위한 저장 정책이 필요하다.

## 5. 통합에서 먼저 해결할 사항

### A. URL 대신 온나라 문서 정체성

온나라의 최상위 URL이 유지된 채 iframe 목록이나 문서가 바뀔 수 있다. sAIde의 현재 URL 중심 대화 분리, 같은 URL 첨부 유지, URL별 기억 덮어쓰기는 그대로 적용하기 어렵다.

권장: 저장 단위는 기관/업무공간·문서 ID·본문 revision, 실행 단위는 여기에 tab/frame·세션·로그인 과·선택 문서 집합을 더한다. 문서 ID 미확인 상태에서는 임시 맥락으로 표시하고 확정 문서 기억에 합치지 않는다. 계정·부서 전환 시 캐시와 미완료 작업의 유효성을 다시 확인한다.

### B. 온나라 전용 어댑터

목록 읽기, 본문 읽기, 명단 읽기, 배부 준비, 실제 결과 확인을 별도 함수·타입으로 분리한다. 모델이 온나라 selector나 접수 단계를 즉석에서 만들어 실행하는 방식보다 참조 프로젝트의 정해진 절차를 재사용하는 편이 적합하다.

기존 HTML 뷰 복제 방식은 typed 상태 메시지와 React 렌더링으로 바꾸는 것을 제안한다. 프레임 로드·DOM 변경 이벤트와 필요한 보조 폴링을 함께 사용한다. 다른 출처 iframe은 기존 same-origin 재귀 탐색으로 읽을 수 없으므로 발견 시 별도 처리해야 한다.

### C. 본문·첨부 획득

1. 초기에는 사용자 선택 텍스트·붙여넣기·사용자가 제공한 텍스트 파일로 기능 품질부터 확인한다.
2. 실제 온나라 상세보기에서 읽을 수 있는 본문 DOM을 확인해 어댑터에 추가한다.
3. HWPX·PDF 등 파일 종류별 파서와 표·문단·페이지 출처를 보존하는 추출기를 추가한다.
4. HWP·스캔 PDF 등 확장 안에서 처리가 어려운 경우에만 로컬 보조 프로세스 필요성을 검토한다.

파일 이름을 읽는 것, 첨부파일을 얻는 것, 내용을 추출하는 것, 온나라 편집기에 쓰는 것은 각각 다른 기능이다. 비전 지원만으로 전체 문서 OCR이나 HWP 편집이 해결되지는 않는다. 캡처 분석 결과에는 보이는 영역만 읽었다는 범위를 표시한다.

### D. 업무용 검색

개인 열람 기억과 현행 업무분장·내부 지침·확정 처리사례를 별도 컬렉션으로 관리한다. 문서·청크·버전·적용일·출처·삭제 정책을 저장한다. 권한 범위가 달라지는 경우 검색 전에 범위를 필터링한다.

검색은 문서번호·기관명·사업명·연도 등의 정확 일치/키워드와 BGE 임베딩 검색을 결합하고 공문 표본으로 평가한다. 과거 이력보다 현행 업무분장을 우선하고, 폐지·변경된 지침을 현재 기준으로 인용하지 않도록 한다. 검색 점수를 정답 확률로 표시하지 않는다.

### E. 모델과 실행 역할 분리

- Gemma: 요약, 정보 추출, 초안, 근거 설명.
- BGE: 문서·질의 임베딩을 통한 유사 자료 검색. 답변 생성 모델이 아니다.
- 일반 코드: ID 매핑, 수치·날짜 검산, 후보 검증, 권한, 상태 전이, 실제 DOM 동작.

업무 결과는 서비스별 JSON schema와 런타임 검증을 두고 `미확인` 값을 허용한다. Ollama structured outputs 적용을 검토하되 형식 준수가 내용의 정확성을 보장하지는 않는다. 대화와 임베딩은 공통 작업 큐로 조정하고 성능은 실제 장비에서 측정한다.

### F. 로컬 저장과 업무 결과

추론을 로컬로 제한하려면 허용 endpoint·모델과 외부 fallback 여부를 코드로 관리해야 한다. 로컬 저장도 공문 사본을 만드는 것이므로 사용자·부서 범위, 보관 기간, 삭제와 내보내기를 제품에 포함한다.

읽기·초안·준비·온나라 반영·실제 완료를 서로 다른 상태로 표현한다. 자동 접수 확대 여부는 기존 검증을 이식하고 실제 오류 사례와 결과 대사가 확보된 뒤 판단한다.

## 6. 서비스 아이디어 10가지

| 번호 | 서비스 | 구체적 사용 예 | 초기 구현과 선행 조건 |
|---|---|---|---|
| 1 | 공문 핵심·조치사항 카드 | 요지, 우리 과가 해야 할 일, 제출물, 기한, 근거 문장을 한 장에 표시 | 선택/붙여넣기 본문으로 시작. 자동화하려면 본문 어댑터 필요 |
| 2 | 회신·기안 초안 도우미 | 수신문서와 사용자 메모로 회신, 협조 요청, 검토 의견 초안 작성 | 프리셋·스트리밍 재사용. 모르는 수치·일자는 빈칸으로 표시. 초기에는 복사로 사용 |
| 3 | 유사 공문·처리사례 검색 | 작년 같은 조사에 어떻게 답했는지 원문과 확정 답변 검색 | 문서 ID 기반 색인, 업무 지식 업로드, 키워드+벡터 검색 필요 |
| 4 | 담당자·협조 부서 추천 | 현행 업무분장과 과거 사례로 담당자 및 추천 이유 표시 | 기존 배분기를 가장 직접적으로 재사용. 로컬 업무분장 검색 연결 필요. 다른 부서 명단 확보 전에는 협조 부서는 제안만 |
| 5 | 제출기한·후속조치 보드 | 공문에서 기한·할 일을 추출하고 사용자 확인 후 내 업무 목록 등록 | 본문 추출, 날짜 정규화, 독립 업무 저장소 필요. 브라우저 밖 알림은 별도 범위 |
| 6 | 기안 전 검토 | 요청 항목 누락, 본문/붙임 불일치, 합계·날짜, 문체를 검토 | 초안·수신문서·첨부 목록 입력. 수치 검산은 코드. 판단 근거와 수정 전후 제시 |
| 7 | 변경 공문 비교 | 최초 안내와 정정 안내의 기한·대상·서식 변경만 비교 | 두 버전 본문과 표 구조 필요. 코드 diff+AI 변경 의미 설명 |
| 8 | 내부 지침·편람 질의응답 | 이 업무의 처리 절차·필요 서류를 기관 자료에서 찾아 답변 | 사용자가 확보한 지침 자료, 적용일·판본·출처 인용. 모델 상식으로 최신 규정 단정 금지 |
| 9 | 주간 업무보고 초안 | 사용자가 모은 공문·확정 처리기록을 사업별 보고 초안으로 변환 | 수집 범위·기준 시각 표시. 열람을 완료로 간주하지 않음. 상태·수치 집계는 코드 |
| 10 | 업무 인수인계 노트 | 진행 중 업무, 기한, 관련 공문, 과거 처리 방법을 묶어 인계서 초안 생성 | 승인된 문서·메모·확정 이력을 묶는 업무 공간과 버전/내보내기 필요 |

### 추천 우선순위

제품의 대표 경험은 1 → 3 → 2, 즉 공문 이해 → 사례 확인 → 회신 작성으로 제안한다. 일반 담당자가 자주 사용할 가능성이 높다는 가설이며 실제 사용자 인터뷰와 처리 시간으로 검증한다.

첫 기술 검증은 이미 목록 계약이 있는 4와 선택/붙여넣기 입력을 사용하는 1·2로 시작할 수 있다. 이후 자동 본문 읽기와 3·8의 로컬 지식 검색을 붙이고 5·6·7로 확장한다. 9·10은 문서와 처리기록이 축적되면 가치가 커진다. 전면 자동 접수는 초기 제품의 필수 조건으로 삼을 필요가 없다.

## 7. 초기 화면 제안

패널 상단에는 현재 기관/과·화면·대상 문서·읽은 범위를 표시한다. 문서가 바뀌면 결과가 어느 문서에 속하는지 명확하게 구분한다.

- 현재 문서: 핵심, 조치사항, 기한, 관련 사례.
- 작성: 회신 초안, 문체 다듬기, 기안 검토.
- 지식 검색: 과거 공문, 현행 업무분장, 내부 지침.
- 내 업무: 확인한 할 일, 진행 상태, 보고/인계 자료.

하단 자유 질문과 문맥별 버튼을 병행한다. 모든 결과에 사용한 출처와 읽지 못한 범위를 확인할 수 있게 한다. 실제 온나라 반영 전에는 변경 대상과 내용을 보여준다.

## 8. 다음 설계에서 확인할 사실

- 접수대기함 외 문서 상세·기안·발송/처리이력 화면의 실제 DOM과 본문 뷰어 종류.
- 설치 대상 Edge 버전, 확장 배포 정책, 온나라 호스트·버전 차이.
- 주요 사용자: 문서배부 담당, 일반 실무자, 관리자 중 초기 대상.
- 주요 파일 형식, 일반 문서 분량, 로컬 문서 수, 메모리·GPU 환경.
- 지식자료 반입·갱신 방식과 개인/부서 저장 범위.
- 공문 표본에서 요구되는 요약·기한·후보 검색 정확도 및 응답 대기시간.

이 항목들은 현재 브레인스토밍의 진행을 막는 질문이 아니라 실제 구현 단계의 확인 목록이다.
